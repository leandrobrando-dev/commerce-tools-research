Epic 2 — Governed Component Library Wireframes

Developer Console surfaces for Storefront Developers defining and publishing the component library that Business Operators edit against. Governance is encoded at the schema level; operators never encounter schema, they encounter the governance boundary. The console also surfaces each component's behavioral provenance — what works, what doesn't, where it's used.

1 — Library Console & Schema Editor

The Developer Console is where Storefront Developers define, version, and publish the component library. Every component is classified as Green Zone (operator-editable) or Red Zone (platform-protected) at creation time, with field-level edit permissions configured through a clear matrix rather than code-only.

Design Notes

  • Library is the home base — developers land here, not on a welcome page. (FR29)
  • Zone designation is visually unmissable — green pill vs gray pill, plus lock icon on Red Zone names. Governance is encoded at the schema level, not in documentation. (FR13)
  • Behavioral provenance inline — CTR lift column surfaces which components actually move the needle. Developers prioritize maintenance by evidence, not intuition.
  • A11y column — every component's WCAG 2.1 AA status visible at a glance. (FR50)
  • Draft row is highlighted amber — the TestimonialsCarousel draft stands out from published components without a separate screen.
  • Red Zone components show "— platform" for CTR — platform-managed components don't compete on operator performance metrics.
  • Version column uses semver — developer-native format. Current version pill uses brand blue to distinguish from older versions in the popover.

export const HeroBanner = defineComponent({
  name: 'HeroBanner',
  version: '2.2.0',
  zone: 'green',
  category: 'layout',

  variants: {
    dimension: 'clv_tier',
    values: ['new', 'low', 'mid', 'high'],
  },

  fields: {
    headline: {
      type: 'string',
      required: true,
      maxLength: 80,
      permissions: {
        operator: 'edit',
        ai: 'write',
      },
    },
    subheadline: {
      type: 'string',
      required: false,
      maxLength: 160,
      permissions: { operator: 'edit', ai: 'write' },
    },
    cta: {
      type: 'CTA',
      permissions: { operator: 'edit', ai: 'write' },
    },
    backgroundImage: {
      type: 'AssetRef',
      permissions: { operator: 'edit', ai: 'write' },
      a11y: { altTextRequired: true },
    },
    // 🔒 platform-managed below
    linkType: {
      type: 'enum',
      values: ['collection', 'product', 'category'],
      permissions: {
        operator: 'locked',
        ai: 'locked',
      },
    },
    tracking: {
      type: 'Tracking',
      permissions: {
        operator: 'locked',
        ai: 'locked',
      },
      emits: ['view', 'ctaClick'],
    },
  },

  accessibility: {
    wcag: '2.1-AA',
    landmark: 'banner',
  },
});

Design Notes

  • Schema UI + live code preview — developers see the form and the generated TypeScript schema update in real time. The schema is the source of truth; the UI makes it tangible. (FR29)
  • Zone choice is permanent after publish — warning surfaced inline in the section header. Reflects a real platform constraint that must be clear upfront. (FR13)
  • Field-level permission matrix — two independent toggles per field: "operator edit" and "AI can write." Locked fields use a flat gray background, not a big warning. (FR14, FR30)
  • Platform-managed fields stay visible — developers see the full schema including locked fields, so they understand the complete component contract.
  • CLV variant support is first-class — declared at the schema level, renders 4 variants automatically with no runtime logic. Reinforced as an AI-tinted section because variants power AI experience personalization.
  • Accessibility baked in — a11y config (alt text required, landmark role) appears in the schema, not as a separate concern. Operators inherit WCAG 2.1 AA for free. (FR50)
  • "Preview as operator" action in the sub-bar — one click to the governance simulator (Screen 2A). Trust but verify.

2 — Governance Simulator & Publishing

Before shipping a component library version, developers verify that governance behaves as intended by simulating operator access — seeing exactly what a Business Operator will see. Publishing is hot-reload: library updates deploy to tenant storefronts without a full platform redeployment. Every release is versioned, diffable, and rollback-capable.

Design Notes

  • "View as" toggle at the top — developer can flip between Business Operator / AI agent / Developer perspective in one click. The same governance rules are viewed through different lenses. (FR31)
  • Left pane renders the operator's actual property sidebar — this is pixel-equivalent to what the operator will see in Epic 3. Not a mock — the same rendering engine.
  • Per-field edit badges — "✓ editable" vs "🔒 Platform" surfaced inline so developers can audit each field at a glance.
  • Bypass attempt preview — the simulator shows what happens if an operator (or AI agent) tries to write to a locked field via API. A successful 403 response proves the governance is enforced, not just UI-hidden.
  • AI parity rule is visible — "AI cannot exceed operator authority" stated explicitly in the right panel. Prevents the AI from becoming a governance bypass surface.
  • "Governance verified" is a commit action — the blue button isn't cosmetic; it signs off that this simulation was run against this version. A timestamped verification appears in the release audit trail.

Design Notes

  • Release-centric not component-centric — developers ship library versions, not individual components. Matches modern design system workflows (Storybook, Radix, Shadcn).
  • Diff view per change — add / change / deprecated colored inline in dark code blocks. Reuses the visual language of git diff developers already know.
  • Deprecation is first-class — not a delete-vs-keep binary. PromoStrip has a migration target, an auto-migration version, and operators get a visible badge. Reflects real library lifecycle.
  • Hot-reload deployment mode explicit — called out with an icon and plain-English explanation. The whole point of FR32 is "no platform redeploy needed" — this is the UI surfacing of that promise.
  • Pre-publish checks mirror Epic 3's operator pre-publish checks — same component, different scope. Developers can see which have passed, which are informational warnings (4 pages using deprecated), and which would block (none here).
  • Scope impact stated plainly — "42 tenant storefronts updated over 60 seconds" helps developers grasp blast radius before clicking Publish.
  • Governance simulator signature required — the check "Governance simulator run at 14:22 today by Leandro" creates a compliance trail: no release ships without explicit verification.

Design Notes

  • Hot-reload makes per-tenant status the primary view — FR32 promises "update without full redeploy." The UX makes that tangible: tenants update in seconds, visible in real time.
  • Tenant-level granularity — each tenant is an independent rollout. Failures isolate; one tenant's bad state doesn't block the others.
  • Per-tenant rollback — "⟲ Rollback" button on successfully-deployed rows. Nothing to wait for — if a specific tenant reports issues, revert that one in isolation.
  • Abort & rollback all — the nuclear option visible at the top, but distinct from per-tenant rollback. Red styling reserved for destructive actions.
  • Progress transparency during deploy — not just "deploying..." but per-phase status: Validating → Installing → Activated. Developers can tell where a slow tenant is stuck.
  • No page navigation during deploy — developers can continue working on the next draft while the deploy runs in this view. Dev console is non-blocking.

3 — Component Behavioral Provenance

Every component accumulates performance data — CTR lift, CLV impact, experiment win rate, where it's deployed. This is the compounding moat: the longer the library ships, the more developers know about what works. Provenance surfaces across two views: a deep single-component view for maintenance decisions, and a library-wide health overview for roadmap prioritization.

Design Notes

  • Provenance is a tab, not a separate tool — developers maintaining this component see its behavioral story alongside schema/version/docs. No context switch.
  • Four headline metrics tell the component's story — CTR lift (Horizon 1 signal), CLV impact (Horizon 2 — the moat), experiment win rate (reliability), and scale (sessions observed). Matches the Epic 8 AI Experience Engine two-horizon model.
  • Variant-level performance breakdown — CLV tier variants don't perform equally. "mid" tier wins at +41.3%. Developers see exactly which variants are carrying the weight, informing where to invest future iteration.
  • Version-anchored annotations — the chart marks where v1.2.0 shipped, so developers can attribute performance changes to their releases (vs seasonal effects).
  • Experiments table reuses Epic 8 vocabulary — H1/H2 horizons, winner/retired states, per-tenant attribution. Same components, same vocabulary across consoles.
  • Retired experiments included, not hidden — "Retired — inconclusive" is honest data. Feeds the Tried and Retired library (Epic 8).

Design Notes

  • Compound CLV is the headline number — "+£1.2M across 42 tenants" frames the library as a revenue engine, not a code asset. This is the metric that converts developers into product thinkers.
  • Winners + retirements side-by-side — the two most actionable lists for roadmap planning. "Invest here" and "stop investing here" at a glance.
  • Scatter plot with invest / retire quadrants — translates abstract data into a spatial metaphor. Developers can see at a glance which components deserve the next iteration.
  • AI suggestions are extraction-focused, not generation-focused — "extract a TestimonialBar primitive" proposes a refactor based on observed patterns. Treats the AI as a pair programmer, not an automator.
  • AI tinting stays consistent — same low-opacity brand-color wash used in Epic 3's AI panel. Operators and developers recognize AI-originated content the same way across the product.
  • Explicit "★ Invest" and "⚠ Retire" quadrant labels — named decisions, not just plotted data. Reflects the Porter-style strategic thinking that should drive library roadmaps.
Wireframes align to the same commercetools Merchant Center design tokens as Epic 3, but the Developer Console surfaces data density and code affordances suited to the storefront developer audience.
