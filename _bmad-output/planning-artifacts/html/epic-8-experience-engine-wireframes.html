Epic 8 — AI Experience Engine Wireframes

The compounding-moat layer of the commercetools Next-Gen Frontend. Once a storefront is live and behavioral data (Epic 5) accumulates, the engine continuously generates hypotheses, runs experiments, surfaces canvas-anchored recommendations with two-horizon measurement (⚡ H1 Quick Win · 📈 H2 Long Game), applies them via progressive rollout, opens GitHub PRs for beyond-Green-Zone changes, and learns from every outcome. Tenant-specific intelligence is the moat — the longer it runs, the smarter it gets.

1 — Canvas-Anchored Recommendation Panel

The Epic 3 editor shell runs unchanged, but its right sidebar transitions into Optimize mode the moment the active page crosses the signal threshold. Recommendations are ranked for the page you're looking at, grouped by campaign, and always framed as "your data shows" — never "the AI recommends." Each recommendation carries a Confidence Card, a Horizon badge (⚡ H1 Quick Win · 📈 H2 Long Game), and an expected outcome with confidence interval.

2 — Experiment Creation & Running

Experiments flow through two entry paths but a single measurement pipeline. Operators author manual hypotheses from the canvas; the engine auto-generates hypotheses when behavioral thresholds are met. Every experiment measures both horizons (H1 short-term signals and H2 long-term CLV / repeat-purchase) in parallel — recommendations surface only after clearing horizon-specific signal gates.

3 — Apply Workflow: Progressive Rollout + GitHub PR

A cleared recommendation is only half the work. Applying it safely to live traffic means progressive rollout through measured gates (5% → 25% → 50% → 100%). When a recommendation needs beyond-Green-Zone changes — new component logic, schema updates — the engine generates a complete GitHub PR: code diff, schema update, behavioral evidence brief, auto-provisioned preview deployment. Zero manual steps between recommendation and merged component.

4 — Engine Calibration: Intelligence Score & Tried-and-Retired

The engine's calibration surface is where the moat becomes visible. The Tenant Intelligence Score summarizes how smart the engine has become for this tenant — it grows with sessions, experiments, and CLV cohort accumulation, and the score cannot be replicated by a competitor connecting to the CT APIs. The Tried-and-Retired library is the other side of the moat: a classified taxonomy of patterns that did not work here, filtering future recommendations so the engine doesn't keep suggesting the same losing ideas.

Design Notes

  • Failure is inventory, not erasure — every retired pattern has a taxonomy label (Underperformed / Selection effect / Guardrail breach / Insufficient traffic / Operator dismissed). Classified failures are more valuable than forgotten ones. (FR60)
  • "Filter applied" is the moat mechanism — each retirement explicitly names the rule derived from the failure. Operators see HOW the engine learned.
  • Cross-tenant learning preserved carefully — "may still propose for tenants with different PDP density profiles." The engine distinguishes "failed here" from "always fails." Prevents overfitting the taxonomy.
  • H1 winner / H2 loser is a first-class pattern — the ExitIntentPopup entry shows a failure mode specific to the two-horizon model. This is exactly why H2 exists; the taxonomy teaches the engine to weight it more.
  • Confidence decay is automatic, not punitive — "won 01-18" is muted, not retired. Flags for re-test instead of retirement. Reflects that commerce behavior evolves and winners age out.
  • Re-test a retired pattern — named action in the sidebar. Retirement isn't permanent; operators can deliberately re-test if they believe conditions changed.
